II.A. Steps to Install All Dependencies
---------------------------------------
To ensure the project is repeatable and can be set up on another machine, this section details the precise process of installing all necessary Python packages for each microservice. This process is performed in the terminal for each service's respective folder.

1. Create a Virtual Environment:
   A virtual environment is a self-contained directory tree that contains a Python installation for a particular version of Python, plus a number of additional packages. Creating one for each service ensures that dependencies do not conflict with each other or with system-wide packages.
   *   Command: `python -m venv venv`
   *   Action: This creates a `venv` folder inside the current service's directory (e.g., inside `user_service`).

2. Activate the Virtual Environment:
   Activating the environment modifies your terminal's PATH to point to the Python executable and scripts inside the `venv` folder. This is a crucial step to ensure that `pip` installs packages into the correct location.
   *   Command (PowerShell): `.\venv\Scripts\Activate.ps1`
   *   Action: The terminal prompt changes to include a `(venv)` prefix, indicating that the isolated environment is now active.

3. Install Packages from `requirements.txt`:
   Each service has a `requirements.txt` file that lists the specific packages and versions it needs to run. The `pip` command reads this file and installs everything automatically.
   *   Command: `pip install -r requirements.txt`
   *   Action: `pip` connects to the Python Package Index (PyPI), downloads the specified versions of each library (e.g., `fastapi`, `sqlalchemy`, `pika`), and installs them into the active `venv`. This step guarantees that every developer and every deployment uses the exact same set of dependencies, which is critical for reproducibility.

This three-step process was performed for each of the four services (`user_service`, `billing_service`, `queue_service`, and `orchestration_service`), resulting in four independent, correctly configured environments ready for execution.


III. Detailed Service Architecture Breakdown
--------------------------------------------

A. User Service (`user_service` folder)
.........................................

1.  Description: This service is the **Gatekeeper** of the entire platform. Its sole responsibility is to manage user identity and security. It handles user registration (sign-up) and authentication (login).

2.  Dependencies and Tech Stack:
    *   Tech Stack: Python, FastAPI, PostgreSQL, SQLAlchemy.
    *   Key Dependencies: `fastapi`, `uvicorn`, `sqlalchemy`, `psycopg2-binary`, `passlib[bcrypt]`, `python-jose[cryptography]`, `email-validator`.

3.  Why We Used Them:
    *   FastAPI: To create high-performance API endpoints (`/signup`, `/login`) with automatic, interactive documentation (`/docs`).
    *   SQLAlchemy: To map our Python `User` class directly to a `users` table in the PostgreSQL database (this is called an ORM).
    *   Passlib: To securely hash user passwords. We never store passwords in plain text.
    *   Python-JOSE: To create and manage JWT (JSON Web Tokens), the modern standard for securely authenticating users across different microservices.

4.  The Flow:
    *   Sign-up: A user sends their email/password. The service validates the data, hashes the password, and creates a new user in the database.
    *   Login: A user sends their email/password. The service finds the user, verifies the password hash, and returns a secure JWT access token if successful.

B. Billing Service (`billing_service` folder)
.............................................

1.  Description: This service is the **Accountant**. It manages all logic related to user credits and the "cost" of using the AI models.

2.  Dependencies and Tech Stack:
    *   Tech Stack: Python, FastAPI, PostgreSQL, SQLAlchemy.
    *   Key Dependencies: `fastapi`, `uvicorn`, `sqlalchemy`, `psycopg2-binary`.

3.  Why We Used Them:
    *   FastAPI: To expose endpoints for checking a user's balance (`/balance/{user_id}`) and viewing the model pricing (`/policies`).
    *   SQLAlchemy: To manage the `user_balances` and `credit_policies` tables in the database.

4.  The Flow:
    *   On Startup: The service runs a special "lifespan" function that connects to the database and seeds it by creating the default credit policies (e.g., for `TELUGU_SST_V1`) if they do not already exist.
    *   Balance Check: When a user's balance is queried for the first time, the service automatically creates a record for them with 10,000 free credits.

C. Queue Service (`queue_service` folder)
.........................................

1.  Description: This service is the **Job Dispatcher**. It is the primary entry point for users who want to run an AI task. Its job is to validate the request, create a tracking record, and delegate the actual work to the background system.

2.  Dependencies and Tech Stack:
    *   Tech Stack: Python, FastAPI, PostgreSQL, SQLAlchemy, RabbitMQ.
    *   Key Dependencies: `fastapi`, `uvicorn`, `sqlalchemy`, `psycopg2-binary`, `pika`, `python-jose[cryptography]`.

3.  Why We Used Them:
    *   FastAPI: To provide the `/jobs` endpoint where users submit their tasks.
    *   Python-JOSE: To *decode* the JWT access token provided by the user to securely identify them.
    *   Pika: This is the Python client library for RabbitMQ. We use it to publish a message to the queue, effectively handing off the job to the background worker.

4.  The Flow:
    *   A user sends a request to `/jobs` with their JWT access token. The service validates the token, creates a `PENDING` job in its database, publishes a message with the `job_id` to RabbitMQ, and instantly responds to the user with the `job_id`.

D. Orchestration Service (`orchestration_service` folder)
.........................................................

1.  Description: This service is the **Engine Room**. It is a headless background worker with no API. Its only purpose is to perform the heavy lifting of the AI processing.

2.  Dependencies and Tech Stack:
    *   Tech Stack: Python, PostgreSQL, SQLAlchemy, RabbitMQ.
    *   Key Dependencies: `sqlalchemy`, `psycopg2-binary`, `pika`.

3.  Why We Used Them:
    *   Pika: To continuously listen to the `ml_jobs` queue in RabbitMQ, waiting for new work to arrive.
    *   SQLAlchemy: To connect to the *Queue Service's database* (`queue_db`) to update the status of the jobs it's working on.

4.  The Flow:
    *   The worker script starts and waits for a message on the queue. When one arrives, it updates the job status to `PROCESSING`, runs the simulated ML task, updates the status to `COMPLETED`, and acknowledges the message to remove it from the queue.


IV. The Complete End-to-End Workflow (Flowchart View)
------------------------------------------------------
This is how all four services work together in a single, cohesive flow:

Step 1: Authentication (User Service)
    |
    --> A user logs in and receives a JWT Access Token.

Step 2: Job Submission (Queue Service)
    |
    --> The user sends the Access Token and job details to the `/jobs` endpoint.
    |
    --> The Queue Service validates the token and returns a `job_id` to the user.

Step 3: Hand-off (RabbitMQ)
    |
    --> The Queue Service sends a message with the `job_id` to the `ml_jobs` queue.

Step 4: Processing (Orchestration Service)
    |
    --> The Orchestration worker picks up the message from the queue.
    |
    --> It updates the job status to `PROCESSING` in the database.
    |
    --> (Simulates ML work for 15 seconds)
    |
    --> It updates the job status to `COMPLETED` in the database.

Step 5: Checking the Result (Queue Service)
    |
    --> The user, using the `job_id` they received, polls the `/jobs/{job_id}` endpoint.
    |
    --> They see the status change from PENDING -> PROCESSING -> COMPLETED and can then access their result.
